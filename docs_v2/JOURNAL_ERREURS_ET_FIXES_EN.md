# Errors and Fixes Log (V2)

This document tracks the anomalies encountered during the development and operation of Smart Robotic Cell V2, along with their root causes and the fixes put in place, to ensure traceability and continuous improvement (NF EN 9100).

**Component legend:**
- ⚙️ **[OT - OPC UA]**: Industrial data server (factory simulator `opcua_server.py`)
- 🌐 **[IT - Web]**: Supervision/dashboard server (FastAPI `web_server.py`)
- 🛡️ **[Global]**: Architecture, cross-cutting security, certificates, or documentation

| ID | Date | Component | Error / Symptom (V2 incidents) | Root Cause | Fix Applied |
| :---: | :---: | :--- | :--- | :--- | :--- |
| **INC-V2-001** | 2026-04-18 | 🛡️ [Global] | `DeprecationWarning: datetime.datetime.utcnow() is deprecated` during SSL certificate generation (`generate_certs.py`). | Python 3.12+ deprecates the use of `utcnow()` in favor of timezone-aware datetime objects. | Use `datetime.datetime.now(datetime.UTC)` (to be fixed in a future minor patch). The warning does not currently block key generation. |
| **INC-V2-002** | 2026-04-18 | 🌐 [IT - Web] | `FileNotFoundError: [Errno 2] No such file or directory` (Uvicorn SSL error) when launching `web_server.py`. | The path to the SSL certificates (`../certs/...`) was not resolved correctly because the terminal was pointed at the project root, causing an extra directory level to be traversed. | Use of absolute paths built dynamically with `os.path.abspath(__file__)` to guarantee the certificates are found regardless of where the script is launched from. |
| **INC-V2-003** | 2026-04-18 | ⚙️ [OT - OPC UA] | Server crash: `BadTypeMismatch` when writing the `TemperatureMoteur` (MotorTemperature) variable. | Python was attempting to write an integer (`int`) such as `60` or `20` into an OPC UA variable initialized as `Double` (float). OPC UA is very strict about typing. | Forced conversion to `float()` when writing temperature variables (`60.0`, `float(round(...))`). |
| **INC-V2-004** | 2026-04-18 | ⚙️ [OT - OPC UA] | `OSError: [Errno 10048] [winerror 10048] only one usage of each socket address is normally permitted` | A "zombie" leftover Python process from the OPC UA server had not been closed properly and was holding port `4840` in the background. | Identified the process via `netstat -ano | findstr :4840` (PID 5880) and force-killed it via `taskkill /F /PID 5880`. |
| **INC-V2-005** | 2026-04-18 | 🌐 [IT - Web] | "Incorrect credentials" when logging in on the web page, followed by "Internal Server Error". | A dictionary key error (KeyError) occurred: the code called `user_dict["hashed_password"]` while the mock database used the key `"password_hash"`. In addition, ghost processes from the old code (`web_server.py`) were running in parallel on the same port 8443, returning random 404 errors on the `/token` route. | Killed all ghost Python processes (`taskkill`), and fixed the hash-key lookup in the password check. |
| **INC-V2-006** | 2026-04-18 | 🌐 [IT - Web] | The web interface did not update with the new design despite reloading the server (browser caching issue). | Browsers (Chrome/Edge) were caching the old HTML version of port 8443 despite the addition of anti-cache meta tags, blocking the display of UI/UX changes. | Changed the web server's listening port from `8443` to `8080` (`uvicorn.run(port=8080)`) to force the browser to treat the page as a new site and invalidate the local cache. |
| **INC-V2-007** | 2026-04-18 | 🌐 [IT - Web] | No cells displayed at all for users anymore (silent JavaScript error). | The OPC UA variable `VitesseBras` (ArmSpeed) did not exist on the new 3-cell data model that had just been deployed, so `cell.speed` was `undefined`, causing a silent JS crash when calling `.toFixed(1)`. | Added a defensive condition `if (cell.speed !== undefined)` in the dashboard's JS script. |
| **INC-V2-008** | 2026-04-18 | 🌐 [IT - Web] | The simulation panel displayed no buttons. | Condition in the JS that was too strict (`innerHTML.trim() === '...'`), which often failed depending on how the browser formatted whitespace/HTML comments, preventing the buttons from being generated. | Replaced the condition with a more robust check: `simuContainer.children.length === 0`. |
| **INC-V2-009** | 2026-04-18 | ⚙️ [OT - OPC UA] | Robot speed remained stuck at 0% in the interface despite the previous JS bug fix. | The `VitesseBras` (ArmSpeed) OPC UA variable had not been recreated during the cell redesign (the variable was lost when moving to the 3-cell design). | Added the `VitesseBras` node and a simulation logic (85-100% oscillation in production, 0% when stopped) to the OPC UA loop. |
| **INC-V2-010** | 2026-04-18 | 🌐 [IT - Web] | The `[DETAILS >]` button remained visible, and the Maintenance alert stayed displayed even after a manual acknowledgment. | The browser kept caching the old version, and the backend did not remove the alert from the dictionary when a fault was acknowledged (`ack_fault`). | Manually removed the alert (`del active_maintenance_requests`) in the acknowledgment function, and changed the port to `8082` to override the cache. |
| **INC-V2-011** | 2026-04-19 | 🌐 [IT - Web] | In the `MAINTENANCE` role, no alert banner was displayed when `HeuresAvantMaintenance <= 10` (HoursBeforeMaintenance, i.e. maintenance imminent). | The JS logic for generating threshold-based maintenance alerts (`<= 10h`) had been removed during successive dashboard changes. | Restored alert generation in `fetchStatus()` (`dashboard.html` template) and reused the `#maint-alerts-banner` banner to display alerts when `time_to_maint <= 10` or `maint_req`. |
| **INC-V2-012** | 2026-04-19 | 🛡️ [Global] | Auth failing in test environment: `/token` returns 401 even though the demo credentials are valid. `passlib`/`bcrypt` warnings visible (`AttributeError: module 'bcrypt' has no attribute '__about__'`). | A bcrypt backend incompatibility/error under certain Python environments, causing an exception during `PWD_CONTEXT.verify(...)` and a systematic login refusal. | Made `verify_password()` tolerant: a controlled fallback in demo mode (via `SRC_ALLOW_INSECURE_DEMO_AUTH`) when the bcrypt check fails, to keep the demo and tests working while retaining the option to disable the fallback. |
| **INC-V2-013** | 2026-04-19 | 🌐 [IT - Web] | Starlette/Jinja2 deprecation warning: `TemplateResponse(name, {request})` no longer uses `name` as the first parameter. | Starlette API evolution: the signature now expects `TemplateResponse(request, name, context)`; the old form is still tolerated but will be removed. | To be fixed in a future patch: adapt the `templates.TemplateResponse(...)` call to the new signature to avoid warnings and prepare for future versions. |
| **INC-V2-014** | 2026-08-08 | 🛡️ [Global] | The workaround put in place for INC-V2-012 remained active by default (`SRC_ALLOW_INSECURE_DEMO_AUTH=1`): `verify_password()` accepted `"ope123"`/`"maint123"` in plaintext without ever checking the stored hash, as soon as passlib failed — i.e. systematically in this environment. Residual risk left unaddressed for security evidence C1.8/C1.10. | The root cause of INC-V2-012 (passlib/bcrypt version incompatibility) had never actually been fixed, only worked around. The plaintext fallback masked the problem rather than resolving it. | Removed passlib as the verification method: `verify_password()` now uses `bcrypt.checkpw()` directly (the same library already used to generate hashes in `db.py`), which does not have passlib's version-detection bug. The plaintext fallback was removed entirely — no more silent bypass, even if passlib fails. `requirements.txt` updated (`passlib[bcrypt]` → `bcrypt`). Tests `test_verify_password_real_bcrypt` and `test_verify_password_rejects_malformed_hash` added to replace the old test, which only tested the workaround. |
| **INC-V2-015** | 2026-08-08 | 🌐 [IT - Web] | Non-regression check after the DB/bcrypt overhaul (CHG-V2-036 to 038): a cold install of the project (`python -m venv` + `pip install -r requirements.txt`) fails at test collection with `ModuleNotFoundError: No module named 'jinja2'`, triggered by the `Jinja2Templates` import in `web_server.py`. | `jinja2` had never been listed in `requirements.txt`, even though `fastapi.templating.Jinja2Templates` depends on it directly; the development machine already had the package installed (independently, or via an old transitive dependency), masking the missing explicit declaration. | Added `jinja2` to `requirements.txt`. Re-verified with a fresh install in a clean environment: all 21 tests pass, and the server starts and responds correctly over HTTPS (`/token`, RBAC on `/api/maintenance/history` and `/api/simu/action` manually tested under real conditions). |
| **INC-V2-016** | 2026-08-19 | 🌐 [IT - Web] | `ReferenceError: Chart is not defined` on `/cell/{id}`: the trend charts never displayed (blank page instead of graphs). | The external `cdnjs.cloudflare.com` CDN loading Chart.js failed to load — outbound network access is not guaranteed on an industrial supervision workstation. Diagnosed with a real browser (Chromium driven via Playwright, console capture) rather than assumed. | Chart.js was vendored locally (`npm install chart.js@4.4.4`, the UMD build copied into `src_v2/static/`) and served by the server itself via `StaticFiles` (see CHG-V2-045). |
| **INC-V2-017** | 2026-08-19 | 🌐 [IT - Web] | Even after the INC-V2-016 fix, the charts displayed with no time markers on the x-axis at all (empty axis under the plotted lines). | The `parsing: false` option passed to Chart.js is incompatible with a `type: 'category'` scale: it prevents Chart.js from building the list of categories (time labels) from the supplied `{x, y}` points. | Removed `parsing: false` in `lineChart()` (`cell_detail.html`, then carried over into `data_comparison.html`), letting Chart.js natively extract the categories from each point's `x` field. | **INC-V2-018** | 2026-08-19 | 🛡️ [Global] | Reported by the user: historical demo faults appeared "active" (unresolved) in the fault history, even though no robot was actually in a faulted state on the OPC UA side — a visible inconsistency between the history and the live dashboard. | The fault history (`DefautHistorique`) is an audit table decoupled from the live OPC UA state (`EnDefaut`): a historical fault inserted with `resolu=False` has no link to the robot's actual state. The demo data generation script (first version) inserted some demo faults without marking them resolved. | All faults generated by `seed_historical_data.py` are now inserted with `resolu=True` (they are already-closed historical incidents); a correction function (`_resolve_seeded_faults`, backed by `SEED_MARKER`) allows retroactively fixing already-deployed data without ever touching a fault actually triggered by a user from the simulation panel. |
| **INC-V2-019** | 2026-08-19 | 🛡️ [Global] | A risk of real data loss was identified and avoided before it happened, while fixing INC-V2-018 on the deployed environment. | The first version of the fix script (`_clear_previously_seeded_tables`) planned to indiscriminately wipe all rows of the `MesureAxe`/`MesureCellule`/`DefautHistorique` tables before regenerating the demo dataset. In the meantime, the deployed server had already started accumulating real production data (readings plus a fault actually triggered by the user), which would have been deleted without distinction. | Systematic verification (comparing row counts and the actual content of the deployed database) before any destructive operation, rather than blind trust in the originally planned script. All destructive logic was removed: `seed_historical_data.py` was made idempotent and non-destructive — it checks the existing state before writing and never touches data that is already present (see CHG-V2-046). |
| **INC-V2-020** | 2026-08-20 | 🛡️ [Global] | Reported by the user: the temperature/current/torque curves on the cell detail page showed abnormal, repeated "jumps backward" on the historical portion (data generated by `seed_historical_data.py`), absent on the recent portion (real-time sampling). | `_is_running(moment)` drew a completely independent production/stopped state at *every* point (every 15 min), with roughly 80%/10%/5% chances of production depending on the time of day. Combined with the progressive axis interpolation (0.15-0.25 factor per point, identical to `opcua_server.py`), the target changed on average faster than the axis could converge toward it: each point followed a partial back-and-forth toward a different target than the previous point, producing a sawtooth appearance. The real-time simulator (`opcua_server.py`) does not have this flaw: its production/stopped state only changes on an explicit manual action (persistent by nature), never by repeated random draws. | Replaced with a persistent-state model (`_next_running_state`): each cell's state (independent across the 3 cells) is only re-evaluated with a low probability at each point (`SWITCH_PROBABILITY = 1/12`), giving continuous blocks of roughly one hour before the next switch, like a real production line. See also CHG-V2-056 (reduction of the sampling interval, requested in parallel for denser curves). |
| **INC-V2-021** | 2026-08-20 | 🌐 [IT - Web] | Reported by the user (with screenshots): on `data_comparison.html`, the 5 comparison curves across the 3 cells showed visible "jumps backward" on the date axis (a point dated earlier appearing after a point dated later). Distinct from INC-V2-020: here the data in the database is correct and already sorted chronologically per cell — only the combined display of the 3 cells is at fault. | The 3 cells are sampled one after another within the same iteration of `web_server.py::_sampling_loop`, so their timestamps differ by a few seconds. The 3 datasets were passed to Chart.js without explicit `labels`; on a `type: 'category'` scale, Chart.js then builds its category list in the order it encounters each new timestamp while walking through the datasets one by one (encounter order), not global chronological order — hence the visible jumps backward as soon as the 3 cells' timestamps interleave. | Added `mergedSortedTimes()` in `data_comparison.html`: merges and deduplicates the timestamps of the 3 cells, then sorts them, and the result is passed explicitly as `data.labels` to Chart.js (instead of letting it infer the axis itself). Added `spanGaps: true` so that each cell's line stays continuous on labels where that particular cell has no point (each cell only populates a subset of the shared axis). Verified via screenshot (Playwright) with genuinely staggered data across the 3 cells: strictly increasing date axis, no more jumps backward. |
| **INC-V2-022** | 2026-08-20 | 🛡️ [Global] | Reported by the user: every timestamp displayed on the dashboard (measurements, faults, maintenance history) showed a 2-hour lag behind the actual time. | All business timestamp writes (`db.py::add_history_entry/add_axis_measure/add_cell_measure/add_defaut`, as well as `web_server.py::get_cell_measures` for the `since` filter and `scripts/seed_historical_data.py`) used `datetime.now(UTC)`. The POC runs on a single machine, in a single timezone (France, UTC+2 in summer), and nothing in the interface converts the stored UTC value to local time on display: the user was therefore seeing raw UTC time directly, wrongly perceived as "running late". | Replaced `datetime.now(UTC)` with `datetime.now()` (naive local server time) in the 4 locations in `db.py`, in `web_server.py::get_cell_measures`, and in `scripts/seed_historical_data.py` — without touching `security.py` (JWT token expiry), which deliberately stays in UTC since it is security data, not a timestamp shown to the user (see the dedicated comment in `db.py`). Verified by running the server with `TZ=Europe/Paris`: a fault forced at 14:56:39 Paris time is correctly recorded and displayed with that timestamp, matching the wall clock. Does not require clearing `smart_robotic_cell.db`: only new rows written after the update reflect local time; rows already stored in UTC are not retroactively shifted. |

| **INC-V2-025** | 2026-09-20 | 🌐 [IT - Web] | Reported by the user while preparing the oral demo: as Maintenance, after resolving a fault via "Intervene" on a cell that also had a pending generic intervention request from the Operator, clicking "Take charge" (this generic request's button) displayed "Error while taking charge." | Resolving a fault (`POST /api/maintenance/intervention`, `probleme_resolu=true`) intentionally removes, server-side, any pending generic request on the same cell (`active_maintenance_requests.pop(...)`, intended behavior: the fixed fault makes the request obsolete).
